Cloning a big repository

A clone brings the whole history: every commit, every version of every file, every branch, and then writes every file. For most repositories that's what you want. For a big one it can be most of a day. The Linux kernel, for one, is 1.5 million commits and 6.8 GB, and writing its 97,310 files took 16 to 19 minutes on a Windows machine.

Git can clone less: part of the history, file contents only when something needs them, one branch, some folders. Git Revenge offers each of these when you clone, and every part of the app copes with a clone that has them.

The clone's options​

Clone a repository, on the start page or from the command palette, has Options under the URL and folder. Folded, a line beside it says what's chosen. Every default is what plain git clone URL does, so a clone you don't change is the clone git would make.

OptionChoicesWhat git does
HistoryEvery commit, the last N commits (of each branch), or since a day.A shallow clone: --depth N or --shallow-since. The history stops at the oldest commit fetched, and more can be fetched later.
File contentsDownload every version now, or only when something needs them.A partial clone: --filter=blob:none. Every commit and folder listing now, and a file's contents the first time something reads it.
BranchesEvery branch and tag, or only one, chosen from the server's branches.--single-branch --branch.
FoldersEvery folder, or only the ones you choose next.A sparse checkout: --no-checkout --sparse, then git sparse-checkout set with the folders.
SubmodulesClone them too.--recurse-submodules, shallow or partial as the clone is.

What each costs, measured on the kernel over file://, so the machine was also the server, with no network in the way:

CloneSizeTime
Every commit, every version6.8 GB
The last commit only290 MB75 s
File contents only when needed2.1 GB, then 2.5 GB once checked out8.8 minutes, then 16 to 19 minutes writing the files
The same, with only mm/ written22 s to write its 226 files and the top level's

The partial clone's own options stop at file contents (blob:none). Git can also leave out the folder listings (tree:0), but then anything that asks which files a commit changed downloads them a commit at a time: one file's history in the practice repository, 1,406 commits, took 175 seconds and 1,371 downloads. On the kernel that would be well over a million.

Only some folders​

Choose Only the ones I choose, next and the clone fetches the history and folder listings and writes no file. A second step then lists the repository's folders from its own tree, each with how many files it holds. Tick the ones you want: the line under the list says how many files a checkout of them writes, counting what a sparse checkout always keeps (the files at the top, and those directly in the folders above the ones you chose).

Check out writes them. Every folder after all writes everything. Closing the dialog takes the clone away, since a clone with no files isn't one you'd keep.

This clone​

A clone that holds less than the whole repository says so in the sidebar's Repository panel, whoever made it, Git Revenge or git in a terminal. Each row says what the clone has, and has the way to the rest:

RowSaysThe way to the rest
ShallowThe history since a day, and how many commits that is.Fetch more history: a year more, 1,000 commits more, or all of it.
PartialFile contents when they're needed, from which remote.Download them all…: every version of every file in the checked-out branch's history (in a sparse checkout, its folders'), as git backfill does. It says first what it would fetch: how big the clone is now, and how many versions it would download, counted while you decide. On a long history the count can take minutes (the kernel's hadn't finished in ten), so after a few seconds it says so, and the download needn't wait for it.
SparseHow many folders are checked out, how many of the files that writes, and the folders' names.Change folders… opens the same folder list as the clone's second step, with the current folders ticked. Every folder asks first, saying how many files it writes. Patterns that aren't folders show as patterns, and are changed with git sparse-checkout.
One branchWhich branch, from which remote.Fetch every branch: git remote set-branches origin '*', then a fetch.

Each runs as a fetch does: its progress in the toolbar, with Cancel, and the graph and lists catching up when it lands.

Storage​

Git keeps a new object as a file of its own, a loose object, and gathers them into packs now and then. A repository with tens of thousands of loose objects, or dozens of packs, makes every git command slower; on one the size of the Linux kernel, that's a delay you notice. The Repository panel's Storage section, there for every repository, says how it stands, from git count-objects:

  • What the objects take on disk, and how many are loose and how many packs hold the rest. Files in the object folder that are neither, such as a pack left half written, are named too.
  • Run maintenance runs git maintenance run: the tasks your git config enables, or git gc when it enables none. It runs as a fetch does, in the toolbar with Cancel. git prints nothing about its progress when it isn't writing to a terminal, so the toolbar says it's running maintenance rather than how far it has got.
  • It's suggested only when git would act on its own: more loose objects than gc.auto (6,700 unless you've set it), or more packs than gc.autoPackLimit (50). The panel then says which, and the button stands out. Otherwise it's there when you want it, and the panel doesn't ask.
  • Git's maintenance schedule: the panel says whether this repository is on it. Put it on the schedule… runs git maintenance start. That adds the repository to the list in your global git config, and has your system's scheduler (Task Scheduler, launchd, or cron or systemd) run maintenance on every repository in the list, hourly, daily and weekly. Take it off the schedule runs git maintenance unregister, which leaves the schedule in place for any other repository on it.

Where a shallow history stops​

Git lists a shallow clone's oldest commits as if they had no parents, so a graph would draw them as where the project began. Git Revenge reads the commits they really have from .git/shallow and lets their lines run on, dashed, to the end of the graph, into a band that says where the history stops:

The rest of the app says so too:

  • Counts: the count above the graph says "since" that day, and so do the Map, Insights and People. An author who's been quiet since then may only be out of reach, not gone.
  • Blame: a line from before the edge says "before" the edge's day, rather than crediting the oldest commit here with it.
  • A file's history that reaches the edge ends with the same band.
  • A commit at the edge opens with all its files as its own, as a first commit's do, and says its parent wasn't fetched.
  • A merge or rebase whose branches part before the edge would be "unrelated histories" to git. Its preview says so and offers more history, and once that's in, it forecasts as usual.

When a file isn't here yet​

In a partial clone, git downloads a file's contents the first time anything reads it: one request for each file, behind whatever asked. That's fine for one file and slow for thousands. Blame on the kernel's Makefile, left to git, made 1,888 downloads and hadn't finished after 15 minutes; its versions in one request take seconds. So Git Revenge reads with git's downloads switched off (GIT_NO_LAZY_FETCH), finds what's missing, and decides:

  1. One thing you opened downloads by itself. A diff, a file, a file from Find in files, a commit's line counts, the files a merge or rebase preview compares, and the pictures a rendered document shows. It says what it's downloading, has Stop, and nothing else waits for it.

  2. Many files ask first, saying how many, and come in one download. Blame reads every version of a file. A file's history that stops at a rename it can't follow offers Download and follow. Insights counts commits and files at once, and lines changed when you choose Download two weeks of changes. Two weeks of the kernel's line counts left to git made 1,442 downloads and hadn't finished after 15 minutes.

  3. Reads across the history never download. The Map, People, smart filters, branch care, the history search and Find in files at a commit use the commits and folder listings, which a partial clone has. Where one would need a file, it says what isn't here.

What leaves your machine​

A download is the same request git makes for a partial clone: it asks the clone's own remote, the one it was cloned from, for the file versions it names, and nothing else. It happens only as the rules above say. Nothing is sent anywhere else.
